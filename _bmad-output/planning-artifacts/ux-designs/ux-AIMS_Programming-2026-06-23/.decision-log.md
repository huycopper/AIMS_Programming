# AIMS Product Management UX Decision Log

Date: 2026-06-23
Status: draft

## Source Intake

- `Context/AIMS-ProblemStatement-ver3.1.1.md`: Product Manager can add, view, edit, delete products; add/edit one product at a time; delete up to 10 per request; max 20 delete/deactivate operations per day; stock-positive products are deactivated; manual stock adjustments require a recorded reason; product operation history is queryable; invalid operations notify the manager.
- `Context/ScreenStandardizationRequirements.md`: Desktop web browser target; minimum 1366 x 768; Inter font; 6 px button radius; field-level errors below inputs; system errors as top banners; tab order follows visual reading order.
- `_bmad-output/implementation-artifacts/4-1-product-management-crud.md`: Current implemented scope includes Product Manager CRUD APIs, admin product list, create/update form, bulk delete/deactivate, and history query.
- Current UI files: `frontend/src/app/boundaries/product-management-screen/*`.

## Decisions

1. The Product Management screen should be table-first, not form-first.
   - Reason: Product Managers usually start by finding, comparing, and selecting products before acting.

2. Create/edit/history should move into a right-side drawer with tabs.
   - Reason: Keeps the product table visible while reducing the current "everything at once" layout.

3. Product creation and product update share one drawer shell, but the mode must be visibly distinct.
   - Reason: Prevents ambiguity between creating a new product and editing an existing product.

4. Bulk delete/deactivate is a contextual selection action.
   - Reason: It should appear only after one or more products are selected and must use a confirmation dialog.

5. Stock adjustment should be its own tab or section.
   - Reason: Stock change has a special business rule: a reason is mandatory and must be logged.

6. Product history should be a product-scoped timeline.
   - Reason: History belongs to the selected product and should not look like a generic global panel.

7. Field-level validation should be preferred over relying on top banners.
   - Reason: Current validation rules are field-specific, especially price range and subtype required fields.

8. The page should reserve navigation space for Product Manager pending-order review, but pending-order review is out of scope for this specific screen spec.
   - Reason: The problem statement gives Product Manager both catalog and pending-order responsibilities.

## Assumptions

- [ASSUMPTION] Primary users are staff Product Managers using desktop or laptop screens.
- [ASSUMPTION] The app has no mature component library; the spec uses native Angular/CSS components following existing AIMS standards.
- [ASSUMPTION] The redesign should not require backend API changes for product CRUD.
- [ASSUMPTION] Reviewer validation was not run in this pass; this draft is ready for user review or implementation story creation.
